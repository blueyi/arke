# P5-S3: Performance Optimization — Design & Results

## Overview

P5-S3 optimizes the LLVM IR backend kernels until they meet the stage gate:
**LLVM geomean ≥ C-like + 5% on Cat A+C+D** (i.e. LLVM/CUDA-C latency ratio
≤ 0.952×) on an RTX 3060 Laptop GPU (SM 8.6, 6 GB VRAM, CUDA 12.4 / nvcc 13.2).

> **Gate status: ✅ ACHIEVED (2026-07-20).** 6-run latency-weighted geomean
> (median-of-3 per op): best 0.867× / median 0.923× / worst 0.948× → 6/6 PASS.
> See "Gate Achievement" below. Harness: `benchmarks/llvm_vs_cuda_c.py`.

The gate compares the **Arke LLVM backend vs the Arke CUDA-C backend**
(same-backend fairness), NOT vs PyTorch. Both backends consume identical
IRGraphs and are timed kernel-only with CUDA events. Early P5-S3 work
benchmarked vs PyTorch/cuBLAS; that framing is superseded by the LLVM-vs-CUDA-C
gate and is retained only where the kernel design notes still apply.

## Architecture

### Execution Model — CachedModule API

```
                    ┌─── prepare(kernel) ──────────────────────┐
                    │  cuModuleLoadData(cubin) → CUmodule      │
                    │  cuMemAlloc × N → GPU buffers            │
                    │  Build kernel arg array (fixed pointers) │
                    └──────────────── returns _CachedModule ───┘
                                      │
            ┌─── run_fast(cached, inputs) ─┐    ┌─── run_fast_no_copy(cached) ─┐
            │  cuMemcpyHtoD (input buffers) │    │  (data already on GPU)        │
            │  cuLaunchKernel + sync        │    │  cuLaunchKernel + sync        │
            │  cuMemcpyDtoH (output)        │    │  (no copy)                    │
            └───────────────────────────────┘    └──────────────────────────────┘
```

**Key insight:** Module load + alloc/free was 40-57× overhead. CachedModule eliminates it.

### Elementwise Vectorization (OT0)

**Pattern:** float4 vectorized load/store + grid-stride loop + rcp.approx.ftz.f

```
Grid = (total/4/BLOCK_SIZE, 1, 1), Block = (256, 1, 1)

vec_loop:
  %xv = load <4 x float>, <4 x float> addrspace(1)* %X_v, align 16
  ; extract → compute on 4 elements → insert
  store <4 x float> %rv, <4 x float> addrspace(1)* %Out_v, align 16
  %vid_next = add i32 %vid, %grid_stride
  br i1 %more, label %vec_loop, label %tail

tail: ; handles remaining 0-3 elements scalar
```

**PTX output:** `ld.global.v4.f32` / `st.global.v4.f32` → 128-bit coalesced transactions.

### Warp-Parallel Reduction (OT1: softmax, layernorm, rmsnorm)

**Shape-adaptive block size** (matches CUDA-C `rowwise_block_for_n`): N≥2048
→ 512 threads (16 warps); else 256 threads (8 warps). This was the single
biggest gate lever — CUDA-C used 512 threads for the N=4096 benchmark shapes
while LLVM was stuck at 256, so Cat C ran ~1.4× slower purely on thread count.

```
Grid=(M,1,1), Block=(nthreads,1,1)  ; nthreads = 512 if N>=2048 else 256

; Each thread processes elements at stride=nthreads
loop:
  %j = phi i32 [%tid, %entry], [%j_next, %body]
  %acc = phi float [INIT, %entry], [%new_acc, %body]
  %j_next = add i32 %j, nthreads

; Level 1 — intra-warp reduction: 5-step shfl.sync.down via inline PTX
; Level 2 — cross-warp reduction: smem[num_warps] + barrier + balanced tree
;   generated by _cross_warp_reduce_ir(num_warps, ..., op="add"|"max")
```

**Online softmax (Milakov & Gimelshein):** 2-pass instead of 3-pass.
- Pass 1: Simultaneous running_max + running_sum with online correction
- Pass 2: exp(x - max) * inv_sum → fused normalize

**FMA contraction:** normalize/accumulate `fmul`+`fadd` pairs carry the
`contract` flag so llc fuses them into `fma.rn.f32` (layernorm affine,
variance; softmax online-update; rmsnorm sum-of-squares). Marginal on
memory-bound reductions but free.

### Tensor-Core Matmul (OT2) — the compute-bound lever

Large TC-eligible shapes (M%64==0, N%128==0, K%16==0, M,N≥1024) route to a
**wmma (Tensor Core) kernel** emitted as LLVM IR with inline PTX. fp16 inputs,
fp32 accumulation (m16n16k16). Smaller/unaligned shapes fall through to a
float4-vectorized double-buffered scalar FP32 ladder.

Final TC kernel configuration (`llvm_wmma.py`):

```
128×128 block tile, 2×4 warp grid (WM=2, WN=4, WTM=4, WTN=2), 256 threads.
Each warp owns a compact WTM*16 x WTN*16 = 64×32 sub-tile.
Double-buffered shared memory (2-stage software pipeline):
  LOAD_TILE(buf 0); barrier
  for kt: prefetch next tile → buf[nxt]; load frags from buf[cur]; 8× wmma; barrier

ptxas: 128 reg/thread, 16 KB smem, 0 spill → 2 blocks/SM (33% occupancy).
```

Three iterations got here (each verified on-device, kernel-only):
1. **2×2 warp grid (64×128 tile)** — replaced a naive 1×4 strip that blew
   registers (140/thread) and crushed occupancy. Fragment reuse: 6 loads
   (2 A + 4 B) feed 8 mma. matmul 1024: 567→529µs.
2. **Double-buffering (staging-level)** — prefetch next K-tile's global loads
   while the current tile computes. matmul 1024: 529→473µs.
3. **128×128 / 2×4 grid** — 4× larger tile amortizes global→shared staging
   over more mma; register pressure *drops* to 128/thread, occupancy 25→33%.
   matmul 1024: 473→388µs.

**Key finding (corrects an earlier note):** double-buffering is *not* always
slower in LLVM IR. Fragment-level buffering IS harmful (inline PTX `wmma.mma`
is `sideeffect` asm and can't be reordered → no overlap). But **staging-level**
buffering wins: the global→shared path is plain `load`/`fptrunc`/`store` (not
sideeffect asm), so ptxas overlaps next-tile global loads with current-tile
tensor-core compute — exactly like CUDA-C's `LOAD_TILE(nxt)/compute(cur)`.

### Fast Math Intrinsics

| Operation | Old | New | Speedup |
|---|---|---|---|
| 1/x | `fdiv float 1.0, %x` | `@llvm.nvvm.rcp.approx.ftz.f` | ~10× |
| exp(x) | libdevice call | `@llvm.nvvm.ex2.approx.f(x * log2e)` | inline |
| 1/√x | sqrt + fdiv | `@llvm.nvvm.rsqrt.approx.f` | ~5× |

## Gate Achievement (LLVM vs CUDA-C, RTX 3060 Laptop)

### matmul progression (the compute-dense lever)
| Stage | matmul 1024×1024 | LLVM/CUDA-C ratio |
|---|---|---|
| P5-S3 start (scalar FP32, no TC) | — | ~1.22× |
| 2×2 warp grid | 529µs | ~1.05× |
| + double-buffering | 473µs | ~1.01× (parity) |
| + 128×128 2×4 grid (final) | **388µs** | **0.705×** (LLVM wins) |

matmul 2048×2048 ≈ 0.66×. Cat D geomean 1.09× → 0.837×.

### Category geomeans (final)
| Category | LLVM/CUDA-C | Notes |
|---|---|---|
| A elementwise | ~1.00× | bandwidth-capped; both backends at the memory wall |
| C reduction | ~0.97× | adaptive 512t closed the thread-count gap (was 1.40×) |
| D matmul | ~0.84× | Tensor-Core kernel now beats hand-written CUDA-C |

### Gate metric (measurement methodology, approved by Leon 2026-07-20)
The gate uses a **latency-weighted geomean** over Cat A+C+D — each op's
log-ratio is weighted by its CUDA-C reference latency — with each op's latency
taken as the **median of 3 measurement passes**. Rationale: the plain
arithmetic geomean weights every op equally, so 7-15µs tiny-shape kernels
(e.g. 32×4096, where launch/dispatch overhead dominates and run-to-run CoV
reaches 16-62%) count as much as 400µs compute/bandwidth-bound kernels,
injecting measurement noise that real kernel throughput does not have.
Weighting + median-of-3 cut gate CoV from ~4.9% to ~3.2%. **The 5% target
itself is unchanged.** See `docs/roadmap/plan.md` P5-S3 [†] footnote.

| Metric | 6-run result |
|---|---|
| Latency-weighted geomean (gate) | best 0.867 / **median 0.923** / worst 0.948 → **6/6 PASS** |
| Unweighted arithmetic geomean (reference) | median ~0.986, CoV 4.9%, 3/10 (noise-dominated) |

Per-op stability (6-run median + CoV): big shapes (≥30µs, 10 ops) geomean
0.960× at CoV 0-7% (stable, real throughput); tiny shapes (<30µs, 13 ops)
geomean ~1.006× at CoV 16-62% (launch-overhead noise). The gate metric is
designed so the stable, throughput-representative kernels drive the verdict.

## Correctness

- reduction (softmax/layernorm/rmsnorm): max_err ~1e-6 vs PyTorch across
  32×4096 / 1024×4096 / small shapes.
- matmul TC: rel_err ~3e-4 (fp16 TC precision class) at 1024/2048.
- Regression: `test_llvm_all_ops` + `test_llvm_backend` + `test_llvm_wmma_correctness`
  = 37/38 pass. The single failure (`test_gelu_and_mul`) is pre-existing
  (since 36b7512, gelu tanh-approx tolerance) and unrelated to P5-S3 kernels.
