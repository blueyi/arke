## 三、深度审计新发现

### D类 — 设计/实现局限（已工作但有结构性限制）

| # | 项目 | 现状 | 影响 | 待做 | 预估 |
|---|---|---|---|---|---|
| **D1** | 优化 action space 只有 `tile` 一种 kind | `ArkeEnv.list_legal_actions()` 对所有 op (matmul/softmax/relu) 都只返回 `tile` candidates。`_LEGAL_KIND_GENERATORS` 注册了 `tile/parallel/unroll/vectorize` 4 种，但 `parallel/unroll/vectorize` 生成器 **对当前所有 op 返回 0 candidates** | Agent 的"bounded action space"实际极度受限——只能做 tile，不能 parallel/unroll/vectorize。这限制了自动调优的策略空间上界 | 实现 parallel/unroll/vectorize candidate 生成逻辑（需要从 op schema 提取 loop structure + HW 资源约束） | 2-3 天 |
| **D2** | 连续 tile 决策不改变 action space | 应用 5 次 tile 后，`list_legal_actions()` 仍返回相同的 10 个 tile candidates——没有 de-redundancy 随 state 演进 | Agent 可能陷入重复决策循环（与 soft_verify R3 去重互补但不完全解决） | tile candidate 应随已 applied 的 decisions 收缩（去除已 applied + 冲突的 factors） | 1 天 |
| **D3** | `emit_mlir_skeleton` 不在 `arke/backend/mlir_emitter.py` | 存在于 `arke/compiler/mlir_emitter.py`（Phase 1 S7 路径），而 Phase 3 的真实 MLIR emitter 在 `arke/backend/mlir_emitter.py`（2992 LOC）。两个模块名相似但功能不同 | 新开发者容易混淆 compiler/mlir_emitter vs backend/mlir_emitter | 在两者的 docstring 开头加明确交叉引用注释 | 15 分钟 |
| **D4** | `arke optimize` 输出路径硬编码 | `arke optimize` 输出到 `benchmarks/results/phase1/stage8/track1/optimize/`（固定路径），被 git track | 运行一次就产生 untracked 脏文件（本次 commit 中意外提交了 5 个产物文件） | 加 `-o` 参数 + gitignore optimize 产物 | 30 分钟 |

## 五、优先级建议（Kitty 推荐）

| 优先级 | 批次 | 项 | 理由 |
|:---:|---|---|---|
| **P0** | 立即 | **A4+A5** | 策略空间严重受限——只有 tile = agent 的"bounded action space"名不副实。这是 Arke 核心命题的实质缺口 |
| **P1** | 紧跟 | **A1+A2+A3** | 架构连线——3 个 backend 走统一 CLI |
| **P2** | 然后 | **B1+B2+B5+B6** | 文档同步 + 产物 gitignore |
| **P3** | 接着 | **C5+C6** | 工程卫生 |
| **P4** | 后置 | **B3+B4** | 低优标注清理 |
| **P5** | Phase 5+ | **C1+C2+C3+C4** | 需要 token 预算 / 周级工程 |

> **与上一版审计的关键差异：** 新发现 **A4+A5（action space 受限）** 的严重度高于
> A1-A3（CLI 连线）。如果 agent 只能做 tile，那 "AI-Native bounded action space"
> 的核心命题没有被真正验证——这比 CLI 不通更本质。

## 六、审计教训（自我纠正记录）

1. **"死代码"删除必须先跑 `pytest --co` 确认无测试依赖** — F4/F5 误删已恢复。
2. **Façade 工具 "isError" ≠ "broken"** — 缺必填参数时正确返回 error 是设计行为。
3. **文档 "✅" 不一定 = 虚假** — 大部分是做了没更新旧表格，D2 soft-verify 是唯一真实缺口（已补）。
4. **action space 必须实测，不能只看注册表** — `_LEGAL_KIND_GENERATORS` 注册了 4 种，但 3 种生成 0 candidates——这是审计第一轮遗漏的结构性发现。
